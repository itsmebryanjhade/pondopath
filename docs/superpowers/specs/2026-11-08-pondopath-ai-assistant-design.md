# PondoPath assistant, import, and laptop offline design

Updated 9 November 2026 after review and demo-slice scoping. Design and delivery decisions for the fictional-data pilot. Implementation and provider evaluation are pending.

Related work includes [the PondoPath PRD](SoloForge_Cash-Flow_Action_Planner_PRD_v1.0.md) (FR-02, FR-09, FR-13, FR-14, AC-08 and AC-09), [the original assistant evaluation](../../ai-verification.md), and the [implementation plan](../plans/2026-11-08-pondopath-ai-assistant.md).

## Purpose and release slices

Help small Philippine businesses get from existing records to their first usable forecast with fewer fields to type. Improve the signed-in assistant first so owners and finance teammates can understand their cash plan and prepare reviewed follow-ups. Use one Add Records flow for spreadsheet files and the existing Google connection, then add laptop access during outages.

| Slice | Deliverable |
| --- | --- |
| A. Demo chat | One conversational assistant in the existing dialog. Page-aware starter prompts, the **+** menu, explanations and source links, editable follow-up and reminder drafts, and the reviewed customer-reply flow. The demo uses Gemini and the existing workspace allowance. |
| B. Easier setup and intake | Open an existing Excel or CSV file, review the suggested columns once, and confirm eligible invoices and bills together. Reuse Connect Google as the single live connector for the MVP. |
| C. Laptop offline pilot (later) | Save the approved forecast for offline reading and preview a local workbook without internet. Continue review against fresh records when connected. |
| Optional follow-up (later) | Evaluate one downloadable local model on laptops. Add focused **Ask AI** shortcuts later where the existing dialog needs a faster entry point. |

**First release (hackathon demo slice) and build order.** The first release is online only: the cloud assistant, adding records and reviewing them all need a connection. Build in this order: the shared provider and usage foundation with Gemini and the existing daily allowance; the one-review workbook setup with **Help match columns**; faster manual entry, including **Add a record from text**; then the chat with source links and **Review draft**. The optional OpenRouter backup, the per-member per-minute limit and its new table, any rework of the Google connection, laptop offline access, the local model and the page shortcuts follow the demo. The existing Google connection keeps working.

**No AI works offline.** When offline access is added later it only lets a person read a saved forecast and preview a local file with PondoPath's programmed rules. Nothing is saved to records and no assistant is available until the connection returns.

The pilot uses controlled fictional demo workspaces and sample messages. The assistant covers PondoPath, cash flow and collections in English, Tagalog and Taglish with automatic language matching. Laptop offline access is opt-in. Phones use the online workspace and server assistant. Direct QuickBooks and Xero connections, invoice-photo extraction and shared financial editing across offline devices are separate expansion decisions. Use exported Excel or CSV files for the first pilot.

## Assistant experience

Keep the signed-in launcher, native dialog and workspace styles. Use the MIT-licensed `@assistant-ui/react` `LocalRuntime` and chat primitives for the thread, message list and composer. The composer accepts ordinary questions. Empty chat shows up to three page-aware starters, and **New chat** clears the conversation. Close and reopen retains it in memory during that signed-in workspace visit. Sign-out, a different actor or business, or **New chat** clears it and discards any late response. Keep one request in flight per dialog. Retain the input after a failed request and let the person choose a retry.

The **+** control is a button named **Workspace tools**. Open it by click or keyboard, close it with Escape, and return focus to its trigger. Keep the composer, menu and draft review usable at phone width. Each item prepares the composer and exposes the selected context. The user can edit the question before **Send**.

| Shortcut | Context and behavior |
| --- | --- |
| **Ask about this page** | Use the active Forecast, Cash, Overview, invoice, bill or Follow-ups context and offer a relevant question. |
| **Draft a follow-up message** | Draft a reminder for an unpaid invoice. Preselect the current invoice when possible and use the existing invoice picker elsewhere. |
| **Plan a follow-up task** | Prepare an internal next action and suggested due date for an unpaid invoice. Open the normal editable follow-up form with the current member as the default assignee. |
| **Understand a customer reply** | Select one invoice and paste the original fictional reply into a separate input. Use the existing extraction and review flow, including the original wording and calculated cash impact. A claimed payment goes to verification. |
| **Add a record from text** | Paste or type a short note, such as an invoice or a bill. The assistant proposes up to three records that open one at a time in the existing Add invoice or Add expense form for review. See [Faster manual entry](#faster-manual-entry). |

Opening the launcher, selecting a tool, editing text, changing a record selection, or viewing a source or draft makes zero provider requests. In the optional shortcut slice, a named page shortcut opens the same dialog with its page or record context and a prepared question. Use **Send** to generate the result. Put the shortcut beside the existing check, invoice action or worklist. For example, Forecast offers **Explain this cash gap** when there is a projected gap, and a Review Inbox row offers **Explain what changed** for an open item. Existing saved tasks and their ordering stay authoritative.

An answer contains brief plain text, app-rendered facts, links to supporting records, and at most one proposed action. **Review draft** opens the existing editable form. The assistant neither saves a task nor approves or sends a message when opening that form. An authorized person submits the form using the existing command, current role, revision and idempotency checks. Reminder approval and sending follow the existing owner workflow. Explain unsupported or unclear requests briefly and point to the appropriate workspace action or ask a focused question.

## Request and response contract

Extend the existing `POST /api/assistant` JSON route and keep the request and response shapes for `explain`, `extract_reply` and `draft_reminder`. The initial tasks (`explain`, `extract_reply`, `draft_reminder`, `chat` and `extract_record`) use the same access, provider and usage checks. Apply those same checks if the later import helper makes a provider request. The demo endpoint selects Gemini on the server. The browser supplies the task and its permitted inputs.

- A `chat` request includes `question` (1–1,000 characters), `expectedRevision`, the existing `language` setting, up to three recent completed question/answer pairs, optional typed page/record context and optional intent `draft_reminder` or `draft_followup`. The intent is a hint for a proposed draft. Invoice actions require an unambiguous authorized unpaid invoice. The paste-reply tool uses the existing `extract_reply` task with its explicit invoice and original reply of at most 4,000 characters.
- Each history pair contains only text (question at most 1,000 characters, answer at most 3,000). Trim the oldest whole pairs first to fit the existing 16 KiB JSON request limit. Server validation still enforces field and byte limits. Treat previous answers, user text, record labels and pasted replies as data. The server supplies the only system instructions.
- Use one strict JSON object per model reply. The chat envelope carries `kind: "answer" | "clarify"`, `summary` of at most 3,000 characters, `factIds`, `recordIds`, and `draft` or `null`. A draft has a kind (`reminder` or `followup`), `invoiceId`, plain text, and a proposed due date for a follow-up. Use existing form length limits and date validation. Each provider receives a supported schema projection. The server validators enforce the full rules before returning a proposal.
- The app adds `sourceRevision`, resolves permitted fact and record IDs to display values, labels and internal links, and verifies draft eligibility against current records. An unknown or out-of-context ID, malformed JSON, refusal or invalid draft is an unusable model reply. Never convert model URLs, HTML, instructions or action names into executable controls. Render only text, validated facts, safe links and supported review forms.

Keep reply sources separate from chat history. An explicitly selected invoice and the exact customer reply are required for extracting a proposed payment expectation. Extend the existing quote, ambiguity and claimed-payment checks with source-value matching. A review-ready proposal must match one distinct PHP-marked amount and one distinct valid full ISO calendar date in the original reply. Exact source quotes must contain both values, together or in separate quotes. Accept `PHP` or `₱` amounts, with correct comma grouping and up to two decimal places, and normalize with the app's money parser. Unsupported formats, conflicting values or a mismatch require `needsReview`, a blank unsupported field, the original reply and a reason for review. Withhold the prefilled confirmation form in that state. When following up in chat, ask the person to clarify a missing date or choose an invoice if context does not identify one.

## Workspace context and freshness

Derive the actor, business and role from the signed-in Supabase session and current membership. Use the existing signed-in client and authorized snapshot. Apply the current revision check before reserving an attempt and re-read the snapshot after inference with a fresh RPC. Reject a reply if membership, business, role, access, demo eligibility or revision changed. Disable stale draft controls on the client and rely on the existing server checks on save.

Use the existing `calculateForecast` output, open worklist and current invoice and bill records. Prefer a valid selected record or an exact invoice number in the authorized snapshot. If there are multiple matches, ask the person to choose. For general questions include the existing 30-day facts and up to 30 relevant invoices and 30 bills, with a note when records are omitted. Project amounts and dates into bounded fields and include only source IDs from the records sent. Keep app help to a short vetted set drawn from the [product guide](../../product-guide.md). This uses existing structured lookups without a separate index or embeddings.

The app renders authoritative balances, amounts and dates directly. Prompt the model to explain the app-supplied facts, distinguish expected payments from received cash, and keep suggestions to actionable PondoPath steps such as verifying payment or preparing a reminder. Send only the fields required for the task. A targeted reminder uses its invoice facts and fictional display label. Exclude email, phone, contact details, raw imports, audit payloads, credentials and unrelated records from provider requests. User-selected customer reply text is the source for the extraction task.

For the optional shortcut slice, bind the Review Inbox shortcut to one authorized item ID, `review_version` and an open status (`pending` or `needs_match`). Send a narrow comparison of allowed structured fields. The item can change without advancing the business revision. Re-read the item's membership, status and version after inference as well as the workspace revision. If it was changed, applied, rejected or superseded, return the refresh state. The explanation links back to the normal Inbox review.

## Provider and spending rules

| Decision | Behavior |
| --- | --- |
| Primary | Use server-side `fetch` with the Gemini Developer API and the stable `gemini-3.1-flash-lite` model. Use an unbilled Google AI Studio project on the Free tier, bounded text input and output, and a structured JSON response. Verify the project's actual free quota before enablement. The stable model ID is documented. The actual project allowance depends on the account. [Gemini model](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite) |
| Backup (after the demo) | Reuse the existing OpenRouter transport with a single named `:free` model and exact provider endpoint that have passed the fictional evaluation. Pin the full endpoint slug when a provider has multiple variants. Require structured output support, keep provider fallbacks disabled and `data_collection: "deny"`, and require zero price for prompt, completion and any per-request charge. Disable backup if no route meets all requirements. |
| Attempts | Each **Send** tries Gemini once. On a provider rate limit, timeout or temporary failure, keep the input so the person can edit or send again. Local clarifications make no provider request. |
| Other failures | Bad input, app limits, stale records, permission errors, missing configuration and invalid model output show a specific recovery state and preserve the regular workspace actions. |
| Timeout and logs | Keep the 20-second provider timeout and existing bounded response read. Log only safe operational details such as provider, failure category, elapsed time and token counts. Keep credentials, messages and record data out of logs and the client bundle. |

Google may use data from unpaid services to improve its products. Enable the feature only for the operator-selected seeded fictional demo workspace with `is_demo` true, and tell people to use fictional records and sample replies. Do not invite real businesses to use the free routes. Using real records needs a separate privacy review and, most likely, a paid or no-training route. A server-side opt-in business ID gates provider access. The planned rollout includes checking billing, availability and privacy terms for the actual routes. ## Supabase usage and authorization

Reuse `public.ai_usage` and the existing `reserve_ai_request(p_expected_revision, p_model, p_provider)` RPC. Reject missing or mismatched expected revisions. A provider attempt reserves one slot before the call, including attempts that time out or fail after reservation. Do not reserve for a rejected request or a local clarification. The demo uses the configured `businesses.ai_daily_limit` per Manila day across chat, legacy tasks and optional cloud mapping help. The planned demo setting is 30. Task 1 adds the hard cap and member limit after the demo. Use the real clock, independently of the fictional forecast date. Exceeding the shared cap returns `AI_LIMIT` and HTTP 429.

After the demo, add one private counter row per membership, keyed by `(business_id, user_id)` with a cascading foreign key to `public.memberships`. Store the current UTC minute start and accepted count. In the same reservation transaction, enforce **five requests per member in each clock minute**. A newer minute resets the row and an older request cannot reset it backward. Reject the sixth with `AI_MEMBER_LIMIT` and HTTP 429. Either rejection rolls back both counter changes. Use the existing private implementation with an empty search path, qualified names, and membership derived from `auth.uid()`. The public wrapper remains `SECURITY INVOKER`. The per-member limit may use a simpler mechanism than a dedicated counter table if it passes AI-05 under concurrency. Any migration needs the owner's explicit approval before it touches the hosted development project.

Keep the private counter outside the exposed API schemas, enable RLS and grant no application table access. Keep existing business-scoped reads and direct write denials on `public.ai_usage`. The signed-in server calls the RPC as the member. A member invoking the public wrapper directly can reserve against their own workspace's shared allowance subject to both caps. That wrapper cannot call a model or expose a key. Treat the daily count as aggregate usage. The RPC's model and provider arguments are not a security or billing audit. [Supabase database functions](https://supabase.com/docs/guides/database/functions) · [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) · [Supabase Data API grants change](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)

## Spreadsheet setup and the Google connection

Start in **Add Records**. Use opening cash and the cutoff date together with what customers still owe and what the business still owes at that cutoff. Bring current balances into review before using them in the forecast. Show the effect of excluded open rows so a partial setup is visible. Carry a partly paid balance only through a verified opening-balance path that preserves the original total when available. If current commands cannot represent that case, put the row in the exception group and show its source values. A status such as “Paid” helps organize history. An actual cash movement requires a verified amount, date and record match.

Use the existing [spreadsheet and review flow](../../product-guide.md) as the starting point. Read the relevant tabs of an existing XLSX or accept CSV. The preview shows invoice and bill totals, rows ready for review, settled history and items that need a decision. Keep the existing file and row safety checks when increasing workbook capacity, and process larger inputs in bounded batches. The current XLSX limit is 512 KiB, which should hold the 300-row IN-01 workbook. Keep it unless that fixture exceeds it, and raise it only with an explicit new bound. Preserve stable source IDs and worksheet and row references. Reuse bulk confirmation for eligible proposals. Retrying after a partial failure preserves the outcome of rows already processed.

Use the current reader and programmed checks for common column names, row types, exact values and duplicate IDs. Offer explicit **Help match columns** for uncertain mappings. Use at most 24 short headers and three masked sample rows from the selected preview. A model can suggest existing column and field choices or report uncertainty. Validate those choices and let the user confirm and save the mapping. Ask once for a shared convention when values are unambiguous after confirmation, such as an omitted year on the same dated sheet. Keep uncertain amounts, dates and record matches in review. Treat pasted customer text through the existing reviewed assistant flow. Keep exact totals, duplicate decisions and writes in PondoPath's rules.

Reuse the tested [Connect Google flow](../../testing.md) for a selected file and tab. The owner signs in and confirms the mapping once. Use one-way pulls into the same Review Inbox and keep the existing **Sync now** action and run status. When the app is open and online again, resume through the existing due checks and source claim so repeated reconnects do not create another run. Keep the last good view when access expires or a header changes, and show **Reconnect** or **Review mapping** as appropriate. An edit made in Google Sheets offline becomes available to PondoPath after Google syncs it. [Google Sheets offline help](https://support.google.com/docs/answer/6388102)

## Faster manual entry

Typing records one at a time is the slowest part of setup, so improve it with programmed help first and one assistant helper second.

**Programmed help.** It needs no AI and works whenever the form works.

- Amount fields accept shorthand such as `25k`, `1.2M` and `₱25,000`, and show the plain amount before saving. A small converter in the form layer produces a plain decimal string. The saved amount still passes the existing `parseMoney` rules and limits.
- An invoice's due date defaults to the plan date plus 30 days and a bill's to the plan date, with quick choices for **Today**, **+7 days**, **+30 days** and **End of month**. The person can always type another date.
- **Save and add another** keeps the form open and the customer chosen, and clears the number and amount. When the last invoice number ends in digits, suggest the next number (for example 1024 then 1025). It is a suggestion the person can edit, and the existing duplicate-number rule still applies on save.

**Add a record from text.** A new `extract_record` task on the same assistant route, with the same access, demo-workspace, provider and usage checks.

- The person pastes or types up to 1,000 characters, for example "Invoice 1042, Northbay, 25k, due Nov 30" or a short bill message in English, Tagalog or Taglish.
- The server returns at most three proposed records. Each has a kind (`invoice` or `expense`), a number or label, a customer name or payee, an amount, a due date and an exact source quote.
- Validate against the source text as for reply extraction. An amount must match one amount in the text, with `PHP`, `₱` or shorthand, and a date must be one unambiguous full date. Anything that does not match is left blank in the form and flagged, not guessed.
- Match a customer only by exact name against the authorized customer list. With no match, the form opens with the **+ Add a new customer…** panel prefilled with the proposed name. Send customer display names only, and only for matching.
- Each proposal opens in the existing form, prefilled and editable. The assistant saves nothing. A record exists only after the person presses the normal **Add** button, which goes through the usual command, role, revision and idempotency checks.

## Laptop offline pilot

**Later, after the demo.** No AI runs offline. Offline access only lets a person read a saved forecast and preview a local file. Changes and the assistant wait for a connection.

After an online sign-in, let the user opt in to a saved forecast on one laptop browser profile. Save the approved forecast figures, plan date, revision and last successful refresh time for that actor and business. Use a 24-hour pilot limit. Keep the saved data in device storage scoped to the signed-in workspace. Cache the public offline screen and its static assets separately from the data. Clear saved data on sign-out, expiry or a different actor or business. Online access and authorization checks govern any resumed review.

With the network off, open the last approved forecast with a visible **Last synced** time. Preview a local XLSX or CSV in the same file flow using programmed checks on-device. Opening and closing the app retains the saved forecast. Reopen the workbook after closing its preview. On reconnect, a user can continue the file review from the open preview after rechecking access, mapping and duplicates. Final confirmation of financial changes uses current online records and permissions. Verify the offline screen and the Excel preview on a real laptop with the network blocked. ## Optional local assistant

After the basic offline flow passes, evaluate one small downloadable model on a supported laptop. Try WebLLM as a candidate and pin a model only after checking its license, storage cost and compatibility. Use the saved forecast to explain app-calculated figures and use a bounded file sample to suggest columns. Validate the same allowed column choices as the online helper. Keep app facts separate from generated text. Report a missing or incompatible model in the laptop view and leave workbook preview available. Measure an offline restart and sample English and Taglish answers before deciding whether to show this in the demo. [WebLLM documentation](https://webllm.mlc.ai/docs/)

## Implementation choices

Use the open-source `@assistant-ui/react` library for the conversation UI. Pin `0.15.33`, whose published React peer range includes the workspace's React 19. Verify installation, type checking and the dialog at implementation time. Do this first as a short spike. If the library conflicts with the existing dialog, fall back to a plain React message list (the dialog is about 120 lines) and keep the same request and response contract. `LocalRuntime` keeps the thread in browser memory and calls `POST /api/assistant` through a small adapter using the current same-origin Supabase session. Mount it within the existing signed-in dialog, with local state and the PondoPath **+** controls. Map validated facts, links and draft cards to app-owned message parts. An explicit Send triggers one request. The runtime receives display data and exposes no model-run workspace tools, cloud history or provider keys.

PondoPath's server owns membership, authorized record retrieval, usage limits, free provider selection and draft validation. Review cards open the existing forms. A generic chat application's authentication, persistence and model settings would also need adapting to these rules. [assistant-ui repository](https://github.com/assistant-ui/assistant-ui) · [LocalRuntime with a custom endpoint](https://www.assistant-ui.com/docs/runtimes/custom/local-runtime) · [Message parts](https://www.assistant-ui.com/docs/primitives/message)

Start with the authority and usage checks, cloud adapters, conversational context and review UI. Any later OpenRouter rollout selects an exact free endpoint and runs its own AI-07 evaluation. Use the intake and laptop checks to decide which capabilities are ready for the fictional-data pilot.
